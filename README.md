# AI Live Chat Agent

A small full-stack web app that simulates a customer support chat for a fictional
e-commerce store. A user opens a chat widget in the browser, asks questions like
_"What's your return policy?"_, and gets answers generated by a real LLM provider
(OpenAI or Anthropic). Every message — user and AI — is persisted to PostgreSQL and
grouped under a conversation/session, so history reloads on refresh.

The system is deliberately layered for separation of concerns and extensibility, and
the LLM vendor is swappable through configuration alone.

> **⚠️ Note on running this app:** I do not have an Paid OpenAI or Anthropic API key, so I
> was unable to run the app end-to-end against a live LLM provider — **no real LLM output
> can be shown here**. The code paths that call the provider are fully implemented, but
> without a valid `OPENAI_API_KEY` or `ANTHROPIC_API_KEY` every turn falls back to the
> graceful-degradation reply (see [Graceful LLM degradation](#trade-offs--scope-notes)).
> To see real responses, supply a valid API key for the selected provider.

## Architecture overview

Requests flow downward through clear horizontal layers. The conversation service is the
channel-agnostic core; the LLM vendor is isolated behind an adapter so it can be swapped
via configuration; the data-access layer owns all database I/O through Prisma.

```
Browser (SvelteKit chat widget)
        │  JSON over HTTP
        ▼
Route layer            POST /chat/message · GET /chat/:sessionId · GET /health
        │
Validation             validate + normalize + truncate inbound payloads
        │
Conversation service   orchestrate one turn: persist user msg → load history
        │                → call LLM → persist AI reply (or degraded fallback)
        ├───────────────► Data access layer (Prisma) ──► Neon Postgres
        │                                                 (conversations, messages)
        └───────────────► LLM service ──► Provider adapter ──► OpenAI / Anthropic API
                              │
                          Knowledge base (persona + store FAQ injected as system prompt)
```

| Layer | Responsibility | Knows about |
|-------|----------------|-------------|
| Route | HTTP concerns, status codes, request/response shape | Conversation service |
| Validation | Input sanity, normalization, truncation | Nothing downstream |
| Conversation service | Orchestrate a turn: persist user msg → load history → call LLM → persist AI msg | Repos, LLM service |
| LLM service | Build prompt, inject FAQ, call provider, map errors | Provider adapter, knowledge base |
| Provider adapter | Vendor-specific request/response translation | One vendor SDK |
| Data access | CRUD on conversations & messages (repositories wrap Prisma Client) | Prisma Client → Neon Postgres |

Key design points:

- **Persist user message before the LLM call** so user input is never lost even if the
  provider fails.
- **Graceful degradation**: any LLM failure becomes a friendly, non-leaking fallback reply
  that is still persisted; the API returns `200` so the chat keeps working.
- **Encapsulated provider abstraction**: the rest of the app talks to a vendor-neutral
  `LLMService`; concrete `OpenAIProvider` / `AnthropicProvider` adapters are selected at
  startup from `LLM_PROVIDER`.
- **Extensible channel model**: a conversation carries a `channel` (default `web`) so future
  inbound channels can be added without changing the core conversation logic.

### Tech stack

- **Backend**: Node.js (LTS, ≥ 20) + TypeScript + Express, Prisma ORM.
- **Frontend**: SvelteKit + TypeScript (chat widget).
- **Database**: Neon serverless PostgreSQL (or any Postgres) via Prisma.
- **LLM**: OpenAI or Anthropic, selectable via environment variable.

## Setup & local run

The backend and frontend are independent npm projects; install and run each separately.

### 1. Backend

From the `backend/` directory:

```bash
# 1. Install dependencies
npm install

# 2. Create your env file from the template and fill in real values
md .env        # on Windows PowerShell: Copy-Item .env.example .env

# 3. Generate the Prisma client and apply the schema (see Neon DB setup below)
npm run prisma:migrate      # prisma migrate dev — creates/applies migrations (uses DIRECT_URL)
npm run prisma:generate     # prisma generate — produces the typed Prisma client

# 4a. Run in development (auto-reload)
npm run dev                 # tsx watch src/index.ts

# 4b. …or build and run the compiled server
npm run build               # tsc -p tsconfig.json
npm start                   # node dist/index.js
```

The server reads its port from `PORT` (default `3000`) and refuses to start if required
configuration is missing or invalid (it names the offending variable without printing its
value). The API is served at `http://localhost:3000`; check `GET /health` returns
`{ "status": "ok" }`.

Available backend scripts (`backend/package.json`):

| Script | Command | Purpose |
|--------|---------|---------|
| `npm run dev` | `tsx watch src/index.ts` | Run the API with hot reload |
| `npm run build` | `prisma generate && tsc -p tsconfig.json` | Compile TypeScript to `dist/` |
| `npm start` | `node dist/index.js` | Run the compiled server |
| `npm run typecheck` | `tsc --noEmit` | Type-check without emitting |
| `npm run postinstall` | `prisma generate` | Generate the typed Prisma client automatically after package installation |
| `npm run prisma:generate` | `prisma generate` | Generate the typed Prisma client |
| `npm run prisma:migrate` | `prisma migrate dev` | Create/apply migrations (dev) |

### 2. Frontend

From the `frontend/` directory:

```bash
# 1. Install dependencies
npm install

# 2. Set it in a .env file or your shell, e.g.:
VITE_API_BASE_URL=http://localhost:3000

# 3. Run the dev server
npm run dev                 # vite dev
```

Available frontend scripts (`frontend/package.json`):

| Script | Command | Purpose |
|--------|---------|---------|
| `npm run dev` | `vite dev` | Run the widget dev server |
| `npm run build` | `vite build` | Production build |
| `npm run preview` | `vite preview` | Preview the production build |
| `npm run check` | `svelte-kit sync && svelte-check` | Type/Svelte diagnostics |

The widget stores its `sessionId` in `localStorage` and rehydrates conversation history from
the backend on load, so refreshing the page continues the same conversation.

## Neon database setup

The Prisma datasource uses two connection strings so that pooled runtime traffic and direct
migration traffic each use the right Neon endpoint:

- **`DATABASE_URL`** — Neon's **pooled** connection string (the `-pooler` host). Used by the
  application at runtime.
- **`DIRECT_URL`** — Neon's **direct/unpooled** connection string. Used by `prisma migrate`
  for schema changes.

Steps:

1. Create a Neon project and database, then copy both connection strings from the Neon
   dashboard (the pooled string contains `-pooler` in the host).
2. Put them in `backend/.env`:

   ```dotenv
   DATABASE_URL=postgresql://USER:PASSWORD@HOST-pooler.REGION.aws.neon.tech/DBNAME?sslmode=require
   DIRECT_URL=postgresql://USER:PASSWORD@HOST.REGION.aws.neon.tech/DBNAME?sslmode=require
   ```

3. Apply the schema:
   - **Local development**: `npm run prisma:migrate` (`prisma migrate dev`) creates and applies
     migrations.
   - **Deployed / CI environments**: run `npx prisma migrate deploy`, which applies the
     committed migrations in `backend/prisma/migrations/` without generating new ones.
4. Generate the client: `npm run prisma:generate`.

The initial migration creates the `conversations` and `messages` tables (with the `Sender`
enum, `uuid`/`timestamptz`/`jsonb` columns, and a `(conversation_id, created_at)` index).
UUIDs are generated server-side via `gen_random_uuid()`, which Neon supports out of the box.

**Seeding**: the store FAQ knowledge base (shipping policy, return/refund policy, support
hours) ships in code — `backend/src/knowledge/knowledgeBase.ts` — and is injected into the
LLM system prompt at runtime. There is no separate database seed step; once migrations are
applied the app is ready to use, and conversations/messages are created organically as users
chat.

## Environment variables

All backend configuration is documented in [`backend/.env.example`](backend/.env.example).
Copy it to `backend/.env` and fill in real values. Startup is fail-fast: a missing required
variable aborts the server before it listens, and the error names the variable without
printing its value.

| Variable | Required | Default | Purpose |
|----------|----------|---------|---------|
| `LLM_PROVIDER` | Yes | `openai` (in example) | Selects the LLM vendor. Accepts only `openai` or `anthropic`. |
| `OPENAI_API_KEY` | When `LLM_PROVIDER=openai` | — | OpenAI credential. Read from env only; never from requests. |
| `ANTHROPIC_API_KEY` | When `LLM_PROVIDER=anthropic` | — | Anthropic credential. Read from env only; never from requests. |
| `LLM_MODEL` | Yes | `gpt-4o-mini` (in example) | Model name passed to the selected provider. |
| `DATABASE_URL` | Yes | — | Neon **pooled** connection string used at runtime. |
| `DIRECT_URL` | Yes | — | Neon **direct** connection string used by `prisma migrate`. |
| `MAX_MESSAGE_CHARS` | No | `4000` | Max length of an inbound user message; longer input is truncated. |
| `MAX_HISTORY_MESSAGES` | No | `20` | Max number of recent messages sent to the LLM as context. |
| `MAX_REPLY_TOKENS` | No | `512` | Max tokens requested from the provider per reply (cost cap). |
| `LLM_TIMEOUT_MS` | No | `30000` | Per-request provider timeout in milliseconds. |
| `PORT` | No | `3000` | HTTP listening port (valid range 1–65535). |

Frontend:

| Variable | Required | Default | Purpose |
|----------|----------|---------|---------|
| `VITE_API_BASE_URL` | Yes | `http://localhost:3000` | Base URL the widget uses to reach the backend API. |

## LLM provider notes (selecting / swapping vendor)

The LLM vendor is chosen entirely through configuration — no code changes required:

1. Set `LLM_PROVIDER` to either `openai` or `anthropic`.
2. Provide the matching API key:
   - `openai` → `OPENAI_API_KEY`
   - `anthropic` → `ANTHROPIC_API_KEY`
3. Set `LLM_MODEL` to a model the selected vendor supports (e.g. `gpt-4o-mini` for OpenAI, a
   `claude-*` model for Anthropic).

At startup the composition root reads `LLM_PROVIDER`, validates it, and constructs the matching
provider adapter behind the vendor-neutral `LLMService`. If `LLM_PROVIDER` is unset or holds any
other value, the server refuses to start and emits a configuration error identifying the invalid
selection. Likewise, if the required API key for the chosen provider is missing, startup aborts
and names the missing variable (never its value).

To add a new vendor later, implement the `LLMProvider` contract once and register it in the
composition root — the route, conversation, and data layers stay untouched.

## Trade-offs & scope notes

- **No authentication (out of scope).** The HTTP API is intentionally unauthenticated to keep
  the assessment focused on the chat pipeline. **For production this is a caveat**: the
  `/chat/*` endpoints would need authentication, authorization, rate limiting, and abuse
  protection before exposure to real users.
- **Static FAQ knowledge base.** Store policy facts are hardcoded in `knowledgeBase.ts` and
  injected into the system prompt. This keeps answers grounded and avoids a retrieval system;
  the `KnowledgeBase` interface allows swapping in a DB- or document-backed implementation later
  without changing callers.
- **Graceful LLM degradation.** Any provider error (timeout, rate limit, invalid key, network)
  is mapped to a typed, user-safe error and turned into a friendly fallback reply that is still
  persisted. The user always gets a usable response and the service stays available, at the cost
  of occasionally returning a generic message instead of a real answer.
- **Cost caps.** `MAX_HISTORY_MESSAGES`, `MAX_REPLY_TOKENS`, and `LLM_TIMEOUT_MS` bound how much
  context is sent, how long replies can be, and how long a call may run. This controls spend and
  latency but can truncate very long conversations' context.
- **Web channel only, extensible model.** Only the web widget channel is implemented, but the
  conversation data model carries an extensible `channel` field so additional inbound channels
  (e.g. WhatsApp, Instagram) can be added without reworking the core conversation logic.
- **Secret handling.** Provider API keys are read exclusively from environment variables and are
  excluded from all responses and logs; raw provider error payloads are never surfaced to clients.
